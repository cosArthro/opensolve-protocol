# 1. 🔴 КРИТИЧЕСКАЯ — обещание «изъять не может никто» ложно; ключ от всего TVL лежит на диске

## Подтверждённые факты

Публичные части ключей из `.keys/` совпадают с вкомпилированными константами:

| файл | pubkey | совпадает с |
|---|---|---|
| `.keys/funding_authority-keypair.json` | `ACbZ5vajyFFseZoYTdrzcxLSJbnnf4pt3MQoZ7XtDrws` | `FUNDING_AUTHORITY`, `lib.rs:34` |
| `.keys/solve_staking-keypair.json` | `GyCrZ9JQq1LAWJ3fWqn52uEnAFUmg52NHQvcatq2mcDe` | `declare_id!`, `lib.rs:20` |

## Сценарий

Программа обновляемая. Держатель upgrade authority публикует новую версию с инструкцией `tag 6 = drain` и вызывает её. Оба хранилища подписываются PDA `["pool"]`, а PDA подчиняется тому байткоду, который в данный момент лежит по адресу программы. Одна транзакция, без таймлока, без предупреждения на цепочке.

По вашему описанию upgrade authority и funding authority — один и тот же ключ. Он нужен еженедельно, то есть он горячий по определению, и при этом сейчас хранится нешифрованным JSON-массивом из 64 байт в рабочем дереве. `.gitignore` содержит `/.keys/`, что защищает от коммита, но не от бэкапа, облачной синхронизации папки, малвари или чтения любым процессом с правами пользователя.

## Последствие

Весь принципал всех стейкеров плюс все залитые награды. Без ограничения по сумме — потолка TVL нет.

## Что сделать до деплоя (по убыванию эффективности)

1. **Отдать upgrade authority мультисигу (Squads) с таймлоком**, либо сделать программу иммутабельной: `solana program set-upgrade-authority --final`. Иммутабельность — единственное, что делает обещание правдой; всё остальное — «доверьтесь мне».
2. **Разделить ключи**, если иммутабельность пока неприемлема: upgrade authority ≠ funding authority. Тогда компрометация горячего funding-ключа не даёт drain.
3. **Funding authority — на аппаратный кошелёк.** Подпись раз в неделю, Ledger подходит идеально.
4. **Убрать `.keys/*-keypair.json` с рабочей машины** совсем.

## Правка формулировки для пользователей

Фраза «изъять принципал или награды не может никто, включая автора программы» в текущей конфигурации неверна. Честная формулировка до перевода в иммутабельность:

# 2. 🟠 СРЕДНЯЯ — funding authority может растягивать выплату наград бесконечно

**Где:** `fund`, `lib.rs:199-209`

**Сценарий.** Каждый вызов `fund` пересчитывает ставку как `(новая сумма + невыплаченный остаток + rollover) / WEEK` и сдвигает `period_finish` на `now + WEEK`. Владелец вызывает `fund(1)` каждый день — каждый вызов заново размазывает весь невыплаченный хвост на новые 7 суток. Асимптотически скорость выплаты стремится к нулю, при этом токены физически лежат в `reward_vault` и не могут быть возвращены никому: инструкции вывода из reward vault нет.

**Последствие.** Не потеря принципала (`unstake` не зависит от authority — см. раздел 13), а бессрочная заморозка наград. Ни стейкеры, ни владелец их не достанут.

**Почему это не «низкая».** Это односторонняя власть authority, не описанная в списке обещаний, и она не требует upgrade authority — достаточно горячего funding-ключа. При его краже вор не сможет ничего забрать, но сможет навсегда заморозить весь reward vault вызовами `fund(1)`.

**Смягчение (выберите одно):**
- потребовать `amount >= MIN_STAKE` в `fund`, чтобы «пыльные» вызовы были дорогими;
- ввести минимальный интервал между вызовами `fund`;
- не двигать `period_finish` при доливе внутрь живого окна, пересчитывая ставку только на остаток.

# 3. 🟠 СРЕДНЯЯ — `fund` блокируется при пустом пуле

**Где:** `fund`, `lib.rs:185-187` (`PoolEmpty`)

**Сценарий A (естественный).** Все стейкеры вышли, `total_weight == 0`. Владелец не может залить награды вообще — а именно наличие наград и вернуло бы стейкеров. Дедлок разрывается только тем, что владелец сам стейкает ≥ 100 000 SOLVE, после чего получает часть собственных наград обратно. Нигде не задокументировано.

**Сценарий B (гриферский).** В пуле один стейкер. Он видит транзакцию `fund` в мемпуле и вставляет свой `unstake` вперёд (если выдержка прошла) → `fund` падает с `PoolEmpty`. Стоимость атаки — комиссия; повторяемо.

**Последствие.** Доступность, не деньги: транзакция проваливается атомарно, токены не теряются.

**Смягчение.** Разрешить `fund` при `total_weight == 0`, положив всю сумму в `rollover_scaled`. Арифметика это уже умеет — ветка `else` в `Pool::update`, `lib.rs:545-550`. Гейт `PoolEmpty` не защищает ни от чего: `update` при нулевом весе и так ничего не раздаёт.

```rust
// было — lib.rs:185
if pool.total_weight == 0 {
    return Err(StakingError::PoolEmpty.into());
}
// стало: убрать гейт целиком — rollover подхватит сумму на следующем стейке
```

# 4. 🟡 НИЗКАЯ — `destination` не проверяется: безвозвратный самосжёг

**Где:** `claim` `lib.rs:275,300`; `unstake` `lib.rs:311,339`

**Сценарий.** Пользователь (или кривой/вредоносный фронтенд) передаёт в `unstake` в качестве `destination` адрес `principal_vault`. Token-2022 разрешает перевод «сам себе» — операция успешна и является no-op. Программа при этом уже обнулила `position.amount` и уменьшила `pool.total_weight`. Итог: принципал остался в хранилище, но учётно больше никому не принадлежит и достать его нельзя ничем, кроме апгрейда программы. То же для `claim` → `reward_vault`.

Чужие деньги так забрать нельзя (нужна подпись владельца позиции) — это foot-gun, не эксплойт.

**Последствие.** Полная безвозвратная потеря принципала конкретного пользователя.

**Правка (2 строки):**

```rust
// в unstake, после require_key(principal_vault, &pool.principal_vault)?;
if destination.key == principal_vault.key {
    return Err(StakingError::WrongAccount.into());
}

// в claim, после require_key(reward_vault, &pool.reward_vault)?;
if destination.key == reward_vault.key {
    return Err(StakingError::WrongAccount.into());
}
```

# 5. 🟡 НИЗКАЯ — двойной учёт при регрессии часов в `fund`

**Где:** `fund` `lib.rs:188, 199-208` вместе с ранним возвратом `Pool::update` `lib.rs:532-535`

**Сценарий.** Пусть `pool.last_update = T`. Приходит `fund` в момент `now = T - Δ` (часы ушли назад). `pool.update(now)`: `applicable = min(now, period_finish) ≤ now < last_update` → ранний `return Ok(())`, `last_update` остаётся `T`. Затем строка 200 считает `remaining = period_finish - now`, то есть включает интервал `[T-Δ, T]`, **уже розданный** в `reward_per_weight` предыдущим `update`. Этот интервал попадает в `leftover` второй раз. Дополнительно строка 208 откатывает `last_update` назад на `now`, и следующий `update` раздаст те же секунды в третий раз.

**Последствие.** Пул обещает больше токенов, чем залито → `claim` последних в очереди падает по нехватке баланса reward vault, и их позиции нельзя закрыть (см. находку 6). Величина = `Δ × rate`.

**Достижимость.** Практически нулевая: Agave в `Bank::update_clock` применяет stake-weighted оценку времени только если она больше родительской, то есть `Clock::unix_timestamp` не убывает. Но код опирается на недокументированную гарантию рантайма вместо собственной проверки.

**Правка (1 строка):**

```rust
// было — lib.rs:179-180
let now = Clock::get()?.unix_timestamp;
let mut pool = Pool::load(&pool_info.try_borrow_data()?)?;
// стало
let mut pool = Pool::load(&pool_info.try_borrow_data()?)?;
let now = Clock::get()?.unix_timestamp.max(pool.last_update);
```

# 6. 🟡 НИЗКАЯ — рента позиции залипает при неплатёжеспособности reward vault

**Где:** `claim` `lib.rs:294-296` (`NothingToClaim` при `reward == 0`) + `close_position` `lib.rs:356-358` (требует `accrued == 0`)

**Сценарий.** Если reward vault не покрывает `position.accrued` (реализуется через находку 5 или через прямую ошибку учёта), `claim` падает на CPI. Обнулить `accrued` можно только успешным `claim`. `close_position` требует `accrued == 0`. Позиция и её рента (~1 426 800 лампортов) заблокированы навсегда.

**Последствие.** ~0.0014 SOL на позицию. Мелочь, но это единственный путь, на котором учёт становится залипающим.

**Смягчение.** Либо разрешить `claim` при `reward == 0` возвращать `Ok(())` вместо ошибки, либо разрешить `close_position` при `accrued != 0` (явный отказ от наград).

# 7. 🔵 ЗАМЕЧАНИЕ — CPI выполняется до записи состояния

**Где:** `stake` `lib.rs:265-267`, `claim` `lib.rs:300-302`, `unstake` `lib.rs:339-341`

Во всех трёх случаях `token_transfer` вызывается раньше, чем `pool.store` и `position.store`. Классический паттерн, на котором ломаются EVM-контракты.

**Здесь это не эксплуатируется** по двум независимым причинам, обе проверены:

1. Рантайм Solana запрещает реентрантность: программа, уже находящаяся в стеке вызовов, не может быть вызвана повторно (разрешена только прямая саморекурсия), возврат — `ReentrancyNotAllowed`.
2. Минт SOLVE не имеет расширения `TransferHook` (подтверждено в mainnet, см. раздел 12), поэтому `TransferChecked` не делает дальнейших CPI — вызывать обратно просто некому.

Тем не менее это защита, целиком заимствованная у окружения. Перестановка двух строк (сохранить состояние, затем перевести) делает свойство собственным. Стоимость нулевая, риск нулевой.

# 8. 🔵 ЗАМЕЧАНИЕ — обещание «остаток подмешивается, а не теряется» верно не полностью

**Где:** `Pool::update` `lib.rs:538-542`, `settle` `lib.rs:377`

`rollover_scaled` ловит ровно две вещи: остаток `funded_scaled % WEEK` в момент `fund` и полную эмиссию за периоды с `total_weight == 0`. Он **не** ловит усечение от `checked_div(total_weight)` в `update` и усечение `/ SCALE` в `settle`. Эти крохи оседают в reward vault навсегда — инструкции подметания нет.

Величина: `update` теряет `< total_weight / 1e18` сырых единиц за вызов (при стейке всего саплая — меньше одной миллионной токена), `settle` — `< 1` сырую единицу (1e-6 SOLVE) на позицию на вызов. Практически ноль, направление верное (в пользу платёжеспособности).

Комментарий «total payouts still cannot exceed total funded» (`lib.rs:198`) правдив. Разговорное «ничего не теряется» — нет.

Там же: «каждый залив размазывается **ровно** на семь суток» — неточно. Он размазывается на 7 суток, если не пришёл следующий `fund` и если пул не пустел. Оба отклонения безопасны, но для пользователей корректнее «до семи суток, остаток переносится».

# 9. 🔵 ЗАМЕЧАНИЕ — посторонние переводы в хранилища застревают навсегда

Оба хранилища — обычные Token-2022 аккаунты по известным PDA. Любой может перевести туда SOLVE. Учёт в `reward_vault` ведётся по ставке, а не по балансу, поэтому «пожертвование» не будет распределено; в `principal_vault` — тем более. Инструкции подметания нет. Не уязвимость, но пользователи, промахнувшиеся адресом, потеряют средства безвозвратно. Стоит упомянуть в README.

# 10. 🔵 ЗАМЕЧАНИЕ — `build.ps1` не проверяет, что именно вкомпилировано

Скрипт грепает `.so` на `BUILT-WITH-`, и это работает: `strip = true` не убирает `.rodata`, литералы `msg!` останутся. Но:

- Нет **позитивной** проверки, что в бинарнике лежат именно `GwyWFsDKW9a2ref1EWqdUS7B37Toii433zrAh9Dipump` и `ACbZ5vajyFFseZoYTdrzcxLSJbnnf4pt3MQoZ7XtDrws`. Опечатка в константе прошла бы весь пайплайн.
- Гарантия действует только для этого скрипта. `cargo-build-sbf --features fast-clock` вручную даёт деплоимый `.so` в обход проверки.
- Нет воспроизводимой сборки и опубликованного хеша: сторонний человек не может убедиться, что задеплоенный байткод соответствует этому исходнику. Для обновляемой программы это важнее обычного.

**Правка:** добавить в `build.ps1` позитивную проверку:

```powershell
foreach ($needle in @("GwyWFsDKW9a2ref", "ACbZ5vajyFFseZoY")) {
    $hit = docker run --rm -v "${project}:/work" $image `
        sh -c "strings /work/target/deploy/solve_staking.so | grep -c '$needle' || true"
    if ($hit.Trim() -eq "0") { throw "Binary is missing expected constant $needle" }
}
```

И публиковать `sha256` каждой задеплоенной версии.

# 11. 🔵 ЗАМЕЧАНИЕ — мелочи

- `lib.rs:211`: `msg!("fund {} spread over seven days from now")` — строка захардкожена, при `fast-clock` она врёт и не упоминает подмешанный остаток. Косметика.
- Состояние помечено магией (`SLVP`/`SLVS`), но **без байта версии**. Программа обновляемая; при смене раскладки различить v1 от v2 будет нечем. Дешевле добавить байт сейчас, чем мигрировать потом.
- `read_u64` (`lib.rs:514`) индексирует `data[..8]` — паника при коротком срезе. Сейчас недостижимо (диспетчер гарантирует `args.len() == 8`), но это единственное место в файле, где корректность держится на удалённом инварианте, а не на локальной проверке. `get(..8).ok_or(...)` бесплатно.
- `stake` не предупреждает, что пул может быть не профинансирован: пользователь запирает деньги на 3 суток при `period_finish` в прошлом и `rate = 0`. Задача фронтенда, не программы.
- Нет структурированных логов (`sol_log_data`). Индексаторы и дашборд TVL придётся строить на парсинге текста — клиент на `solve-staking.mjs:452` уже этим занимается.

# 13. Сильные стороны (проверено целенаправленно, проблем нет)

Раздел приводится не для комплимента, а чтобы было видно объём проверенного.

**Учётная модель.** Порядок `update → settle → мутация` соблюдён во всех пяти инструкциях:

| инструкция | `pool.update` до изменения `total_weight`? | `settle` до изменения `position.amount`? |
|---|---|---|
| `stake` | да, стр. 254 → 261 | да, стр. 257 → 259 |
| `unstake` | да, стр. 324 → 332 | да, стр. 327 → 336 |
| `claim` | да, стр. 289 (вес не меняется) | да, стр. 292 → 297 |
| `fund` | да, стр. 188 → 206 | н/п |
| `close_position` | не вызывается — вес не трогается | не вызывается — требует `amount == 0` |

Отдельно проверен самый опасный сценарий — пересоздание позиции после `close_position`: `Position::new` обнуляет `reward_per_weight_paid`, но `settle` стоит **раньше** `position.amount +=` (строки 257 и 259), поэтому нулевой `paid` умножается на нулевой `amount`. **Если бы эти две строки поменяли местами, новый стейкер забирал бы всю историческую эмиссию пула.** Сейчас порядок правильный — это стоит зафиксировать тестом, чтобы будущий рефакторинг не сломал.

**Арифметика.** Границы `total_weight` (≤ 1e15), `reward_rate_scaled` (≤ 1.65e27), `elapsed` (≤ 604800), `reward_per_weight`, `amount × delta` (≤ 1e33), `earned` посчитаны явно против `u128::MAX ≈ 3.4e38` и `u64::MAX` — запас минимум 5 порядков. Все `checked_*` на месте, ни одного голого `+`/`*`/`-` на пользовательских данных. `overflow-checks = true` в release-профиле (для Solana это не самоочевидно и это правильно). Деление на ноль закрыто охраной `if self.total_weight > 0`. Все три усечения режут в пользу пула.

Переполнение в `settle` (`amount × delta`) отдельно проверено: собственный `amount` позиции входит в `total_weight` на всём протяжении окна между двумя `settle`, поэтому `amount ≤ total_weight` поточечно и `amount × delta ≤ Σ elapsed × rate`. Недостижимо.

**Проверки аккаунтов.** Матрица 6 инструкций × 6 категорий, каждая ячейка сверена со строкой:

| инструкция | signer | адрес PDA | владелец | минт | token program | system |
|---|---|---|---|---|---|---|
| `initialize` | 115 + `== FUNDING_AUTHORITY` 116 | pool 122, vaults 459 | `create_pda` 392 | 117 | 119 | 118 |
| `fund` | 174 + `== FUNDING_AUTHORITY` 181 | pool 175 | 481 | 176 | 177 | — |
| `stake` | 228 | pool 229, position 236 | 481, 247 | 230 | 232 | 231 |
| `claim` | 281 | pool 282, position 501 | 481, 498 | 283 | 284 | — |
| `unstake` | 316 | pool 317, position 501 | 481, 498 | 318 | 319 | — |
| `close_position` | 353 | position 501 | 498 | — | — | — |

Хранилища сверяются не с seed'ами, а с полями пула (стр. 182, 253, 288, 323) — это строже, поскольку пул может ссылаться только на то, что создал `initialize`. Тип аккаунта защищён магией + длиной (149 / 77 / 165 — три непересекающиеся длины). Подстановка токен-программы невозможна структурно: `token_transfer` захардкоживает `program_id: TOKEN_2022` в самой инструкции (`lib.rs:429`).

**Создание/закрытие аккаунтов.** `create_pda` (`lib.rs:392-402`) не использует `system_instruction::create_account` (который упал бы на предзаполненном аккаунте), а делает `transfer(missing) → allocate → assign`, где `missing = rent.saturating_sub(balance)`. Предоплата лампортов на чужой position PDA просто субсидирует жертву. **Это одна из самых частых ошибок в native-программах, и здесь она обойдена.** Создать аккаунт по адресу PDA извне нельзя. Устаревших данных после `resize(0)` + повторного `allocate` не остаётся. Двойного возврата ренты нет. Двойное заимствование `owner`/`position_info` невозможно (один обязан быть подписантом, другой — PDA).

**Отсутствие бэкдоров.** Диспетчер обрабатывает ровно шесть тегов, всё остальное — ошибка; строгие проверки длины аргументов (`args.is_empty()` / `args.len() == 8`) не дают протащить лишние данные. Во всём файле ровно два дискриминатора Token-2022: `12` (TransferChecked) и `18` (InitializeAccount3). Ни `SetAuthority`, ни `Approve`, ни `CloseAccount`, ни `Burn` не встречаются. `#![deny(unsafe_code)]`. Инструкций смены `FUNDING_AUTHORITY`, минта, хранилищ или паузы нет. **Комментарий на строках 132-135 про невозможность делегата и close authority — правда.**

**Доступность принципала.** `unstake` не зависит ни от funding authority, ни от ненулевой ставки, ни от состояния наград. Потеря ключа владельца останавливает награды, но не запирает принципал. Это сильное свойство, оно проверялось целенаправленно.

**Время.** Отсечение по `period_finish` (`applicable = now.min(period_finish)`). Защита от чтения всей эпохи Unix при первом вызове после `initialize` (`last_update = 0`, `period_finish = 0` → ранний возврат). Корректность накопления в `rollover` при пустом пуле. Залив ровно в момент `period_finish` обработан корректно: `now < period_finish` ложно → `leftover` не добавляется, `rollover` всё равно подмешивается, ничего не теряется и не дублируется.

**Реентрантность и заимствования.** Все 11 мест с `try_borrow*` проверены на время жизни `Ref`/`RefMut` — это временные значения в выражении `let`, уничтожаются на `;`, активных заимствований во время `invoke` нет.

**Соответствие клиента программе.** Порядок и флаги аккаунтов во всех шести инструкциях `client/solve-staking.mjs:134-219` совпадают с `lib.rs` строка в строку. Расхождений нет.

# 14. О тестах

Прочитаны тела всех 11 интеграционных и 11 юнит-тестов. **Они честные** — имена соответствуют содержимому, ассерты проверяют состояние, а не факт «транзакция прошла».

Три особенно сильных:

- `payouts_never_exceed_what_was_funded` (`lib.rs:851-932`) — property-тест на 4000 шагов, проверяющий инвариант `claimed + outstanding ≤ funded` после **каждого** шага, с финальным ассертом, что прогон вообще что-то залил и заклеймил (защита от вырожденного прохода).
- `nobody_can_touch_another_wallets_position` (`integration.rs:585`) — не просто ждёт ошибку, а после трёх попыток кражи проверяет нулевой баланс вора и целостность позиции жертвы.
- `initialize_creates_a_pool_and_two_clean_vaults` (`integration.rs:370`) — лезет в сырые байты хранилища и проверяет отсутствие делегата (смещение 72..76) и close authority (129..133).
